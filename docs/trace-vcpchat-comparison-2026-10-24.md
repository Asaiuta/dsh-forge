# Trace 与 VCPChat 的性能对照

日期：2026-10-24。接续 [上一轮修复与优化](trace-optimization-2026-10-24.md)，本轮仅调整 `src/facts.ts` 的节点访问和 `src/web-tree-sitter.d.ts` 的接口声明。保留工作区已有修改，未提交或发布。

后续的批量 wrapper 扫描、Rust / Python / C/C++ 文件依赖及最新复测见[第三轮记录](trace-languages-performance-2026-10-24.md)。本文的时延与语言范围保留为第二轮历史结果。

## 结果

默认 WASM 路径继续提速，无需安装原生索引器。两个冻结语料各运行三个独立进程，以下为冷查询中位数；括号为最小值至最大值。

| 冻结语料 | 候选文件 | 本轮优化前 | 本轮优化后 | 耗时减少 | VCPChat ProjectForge 原生参考 |
| --- | ---: | ---: | ---: | ---: | ---: |
| VCPChat | 1,691 | 8.35 s（7.25–11.86） | 4.79 s（3.55–4.93） | 42.6% | 4.61 s（3.60–5.25） |
| VCPToolBox | 1,430 | 14.63 s（13.55–15.22） | 5.72 s（4.86–6.23） | 60.9% | 2.92 s（2.40–3.26） |

本插件相对本轮基线分别加速 1.74× / 2.56×。首轮单次测量曾显示约 3×，最终采用全部三次样本的中位数。系统负载、GC 和操作系统缓存存在波动，三个样本不构成稳定性能上限或统计显著性证明。

VCPChat 语料上，两种实现的时延接近；VCPToolBox 上本插件仍约为原生参考的 1.96 倍。两产品的事实模型和提取规则不同，这里的对照仅衡量同一文件集合上的事实提取与组图成本，不表示分析结果等价，也不包含完整宿主调用开销。

## 比较口径

- Windows、Node v24.9.0、i5-12500H，`availableParallelism()` 为 16，本插件自动使用最多 8 个 AST Worker。所有测量依次运行，未与构建或全套测试并发。
- 冷查询指新进程中解析、事实和图缓存为空；没有清空操作系统文件缓存。各轮后续两次测量交替本插件基线与优化版的顺序。
- 本插件计时为 `assembleTraceGraph()`，包含扫描、Worker 启动、语法解析、事实提取和组图；不包含模块 import、结果序列化及测试断言。
- 原生参考计时为 `facts` 请求（含 JSON 协议传输和解析）、别名扩展后的必要重扫、`buildGraph()`。原生进程启动和 ping readiness 单列，不包含模块 require、声明表加载、目标查询或展示。启动中位数分别为 47 / 60 ms。
- 两边声明表均为 `absent`。直接调用参考二进制与纯组图模块，没有启动其 Service、SQLite 或执行声明表 registry 加载器。
- PF 计时在 `buildGraph()` 后立即停止，文件清单读取及断言在计时外；早期 `results/reference/` 样本曾包含断言开销，已排除最终汇总，使用重新测量的 `reference-final-1/2/3`。

参考路径为 VCPChat 仓库的 `VCPDistributedServer/Plugin/ProjectForge/` 下 `ProjectForgeService.js`、`indexerClient.js`、`linkGraph.js`，以及 `rust_projectforge_indexer/src/scan.rs`、`src/facts/js_html.rs`。运行的是仓库随附二进制，没有重建参考实现：

参考实现默认会跳过 `vendor`、`assets`、`artifacts`、`target` 等目录。为消除扫描范围差异，本轮按本插件的根 `.gitignore`、扩展名和目录规则冻结源码文件，保留相对目录与原始字节，再将同一份集合交给两边。没有排除 vendor bundle。语料只复制 Trace 源文件，真实仓库中的非源码依赖另做原仓回归。

## 实现取舍

VCPChat 通过 Rust + Rayon 并行提取事实，再由 JS 组图。其 Service 缓存 bridge 别名名单，发现新别名时重扫；本轮 Chat 语料首次请求均为两轮、累计解析 3,380 个文件，Toolbox 为一轮、1,429 个文件。本插件上一轮已将 bridge 筛选与文件提取解耦，避免这种二次解析。

本轮继续优化 WASM 与 JS 之间的节点访问：

1. 将每个节点独立创建 getter 和方法闭包的对象，改为共享 prototype 的 `FactNodeView`，减少对象和闭包分配。
2. 字段缓存 `Map` 按需分配，避免给仅被遍历的节点预先创建空表。
3. 使用 `raw.namedChildren` 批量读取命名子节点，省去生成标点节点及逐个读取 `isNamed` 的跨 WASM 调用。0.25.0 的实际运行时与原厂类型均提供该 API，本项目的最小 ambient 声明同步补充 `(Node | null)[]`。

按节点 ID 去重、叶节点跳过、文本/位置/父节点/字段缓存及原来的遍历顺序继续保留。视图只在一次同步提取期间存在，输出事实不持有节点；语法树仍在 `finally` 中释放。没有引入跨产品代码复制、新依赖或常驻监听器。

当前收益足以支持这次局部结构调整。批量查找特定后代节点会涉及作用域上下文、提前返回和顺序语义的重写，本轮没有扩展至该方向。剩余冷查询成本仍包括完整 AST 的 WASM 解析、节点读取和事实遍历；原生提取可作为后续方向，需要先补齐行为一致性，不能直接将现有符号 sidecar 视为 Trace 后端。

## 重复查询

每个独立进程首次查询后再运行三次，共 9 个热态样本。以下单位为毫秒，中位数后附最小值至最大值。

| 语料 | 本插件优化前 | 本插件优化后 | PF 重复 facts + 组图 |
| --- | ---: | ---: | ---: |
| VCPChat | 560（423–807） | 460（237–570） | 615（465–1,171） |
| VCPToolBox | 428（296–646） | 319（251–385） | 672（488–922） |

本轮没有修改本插件的热查询校验路径，上述变化可能受冷解析后内存状态、GC 与系统负载影响，因此不将它解释为缓存机制的结构性提速。

PF Service 每次均调用 facts 并重新组图，JS 层没有完整图缓存，仅缓存别名名单。上表对应其主要扫描/组图阶段，仍不代表完整产品的端到端热查询时延。

## 本地证据与复跑

证据位于 Git 忽略的 `.tmp-analysis/`：

- `trace-round2/baseline-src/`、`baseline-lib/`：本轮修改前源码与完整构建快照，未被后续构建覆盖。
- `trace-round2/{VCPChat,VCPToolBox}.manifest.json`、`corpus/`：冻结清单及逐文件原始字节。
- `trace-round2/results/baseline{,-2,-3}/`、`node-views/`、`optimized-{2,3}/`：本插件各次图与指标。
- `trace-round2/results/reference-final-{1,2,3}/`：参考实现的正确计时样本、阶段时间、解析轮数与启动时间。
- `trace-round2/summary.json`：全部样本、最小值、中位数、最大值与清单/图哈希。
- `trace-review/node-views-final/`：原始仓库完整输出、指标与更早基线的等价检查。
- `trace-round2-check.log`、`trace-round2-final-tests.log`：本轮构建和全套测试记录。

基准脚本 `trace-round2.mjs` 的 `df baseline[-N]` 加载冻结构建，其他 `df` 标签加载当前构建；`pf` 调用参考实现，`compare` 严格比较完整输出。`trace-round2-repeat.mjs` 按顺序复跑，`trace-round2-summarize.mjs` 重新核验清单字节和全部图后生成汇总。复跑会更新对应测量文件，冻结源码、构建和语料不会重建。
