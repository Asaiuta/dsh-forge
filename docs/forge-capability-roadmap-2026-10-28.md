## 一、目标与取舍

目标不是把 Trace 变成所有语言的编译器，而是让插件能够回答并串起五件事：

1. 应该看哪里，已有证据是否新鲜、范围是否完整？
2. 要修改的究竟是哪一个符号、哪些文件或通信契约？
3. 修改是否完整落盘，有没有漏改消费者？
4. 哪些检查真正执行了，检查针对哪个版本，哪些仍未验证？
5. 失败如何安全恢复，下一次会话如何复用有出处的结论？

推荐路线：**先让现有文件图和 Electron 能力闭环，再接入 JS/TS 符号语义，再扩展专业语言后端。** 搜索、AST、快图、语义、执行验证各司其职，不互相冒充。

不承诺：完整运行时调用图、自动证明修改绝对安全、全语言同等深度、默认自动修复、默认执行项目构建脚本、默认上传代码、默认安装语言服务器。

## 三、闭环形态：复用工具，不建立第二套施工系统

```text
ff_cards / ffhistory ──提供带出处的历史线索──┐
fffind / ffgrep ──定位候选─────────────────┤
                                         v
                           ff_read：读取当前内容与目标
                                         |
                           fftrace：范围、关系、影响
                                         |
                           变更计划：目标 + 基线 + 检查项
                                         |
                           ffedit / ff_file：受控应用
                                         |
                           改后审计：前后证据比较
                                         |
                           显式验证：静态检查 + 宿主检查
                                  /                \
                    未通过 / 未完成                  按约定范围通过
                    修正后重查，或                   历史关联验证证据
                    ffrollback 预览并确认            卡片生成可追溯摘要
                                  \                /
                                  下一次读取重新校验版本
```

### 3.1 工具分工

| 工具 | 联动后的职责 | 明确不做 |
|---|---|---|
| `fffind` / `ffgrep` | 找候选，附可读取的位置和范围信息；在无语义后端时保留文本兜底 | 把同名文本批量当成同一符号改掉 |
| `ff_read` | 读取当前版本；从位置选择真实目标；提供可复核内容锚 | 仅凭旧行号授权写入 |
| `fftrace` | 保留快图；新增按位置的语义引用/调用层次查询；给影响和检查建议 | 把文件依赖、语义引用、静态调用、运行时观察混成一种边 |
| `ffedit` | 应用经确认的文本或语义变更计划，所有入口统一返回批次与审计状态 | 边写边隐式启动全仓类型检查；失败后自动扩大修改范围 |
| `ff_file` | 文件/符号迁移先预览引用更新，支持时转成同一变更计划 | 仅搬文本却宣称已完成语义重构 |
| `ffhistory` | 将写入批次、检查结果、回滚关系连起来，保留原始快照与出处 | 将“执行过命令”显示成“改动已验收” |
| `ffrollback` | 预览恢复范围，检测后续/外部修改，确认后产生新批次，再重查 | 因一次测试失败自动回滚；承诺撤销测试产生的数据库/网络副作用 |
| `ff_cards` | 汇总改了什么、检查了什么、哪些仍未知，引用批次与检查记录 | 将模型润色内容当测试结果；将历史通过当当前通过 |

验证入口拟增加一个薄的 `ffcheck`，这是本文唯一建议新增的公开工具；名称和 schema 的具体草案见[公共契约](forge-plan-contracts.md)，M1 核验后定稿，当前不可调用。它负责静态复查、检查计划、已授权宿主执行的结果归集，不复制终端或成为通用 shell。若宿主没有可用、可关联执行结果的接口，明确返回 `unavailable`，由 Agent 手动执行并作为外部证据展示，不能伪装成自动核验。

### 3.2 只增加三种必要关联

以下是待实施的数据契约，具体字段见公共契约，不是现有接口承诺；先服务一个纵向场景，再抽共用部分。

1. **版本化目标引用**：工作区身份、规范路径、内容哈希、范围及坐标编码；语义结果另带项目配置、后端版本与符号身份。行号用于展示，不充当持久身份；符号移动后也不能假设旧 ID 永久稳定。
2. **变更关联**：复用现有 batch/node 和 before/after 快照；跨多个批次的操作增加轻量关联，不另建一套任务数据库。模型写的 `reason` 说明意图，不充当正确性证据。
3. **检查记录**：关联批次、被检查内容/项目配置、检查项、执行来源、范围、开始/结束、退出码或诊断、结果摘要与受控保存的输出。命令日志是证据，模型的“通过”文本不是证据。

范围信息至少区分：扫描排除、预算截断、解析失败、外部依赖、后端缺失、动态未知与缓存过期。语义边保留 provider、版本、配置和依据；`certain` 仍不等于运行时可达。

不要强制每次廉价搜索都计算全仓哈希：结果进入写入或正式验证流程时才提升身份校验强度。内容身份、项目配置签名与明确检查范围共同界定证据适用面。

### 3.3 完成状态必须由证据导出

写入状态与验证状态分开：`applied` 不等于 `verified`。

- `passed`：该检查确实完成，并满足其明确范围内的判据。
- `failed`：检查发现问题；基线原有问题与本次新增问题分列。
- `partial`：只覆盖部分请求范围，或存在妨碍结论的截断/未知。
- `not_run` / `unavailable`：没有运行或能力不可用，绝不按通过处理。
- `stale`：内容、项目配置或证据身份已变化，需要重跑。

汇总“按约定范围通过”要求：必需检查已执行且通过、没有相关过期结果、没有被隐藏的失败或未知。通过范围必须可见；不是给整个工程盖“安全”章。允许记录显式缩小的验收范围，但必须保留未覆盖项，不能把未知改写为零问题。

## 四、阶段路线图

优先级为推荐实施顺序，不是已批准执行。S/M/L 表示相对工作量，不代表承诺工期；语言后端的环境兼容成本需要先用最小试验确定。

| 阶段 | 交付物 | 依赖 | 工作量 | 完成后新增的实际能力 |
|---|---|---|---|---|
| M0 证据契约与能力边界 | 新鲜度/覆盖状态、审计入口一致性、当前能力矩阵 | 无 | S–M | 不再把没检查当没问题 |
| M1 Electron 最小闭环 | 前后桥接审计、薄验证入口、batch→检查→历史关联 | M0 | M | 不靠 Agent 手工拼接也能发现漏改并追溯验证 |
| M2 JS/TS 语义通道 | 按位置定义/引用、类型诊断、可选调用层次 | M0；复用 M1 验证 | L | 区分同名符号与接收者，给出语义消费者 |
| M3 跨文件安全变更 | 预览、全路径授权、版本校验、恢复、语义后验 | M1 + M2 | M–L | rename/move 从“搬文本”升级为受控变更 |
| M4 专业语言与框架扩展 | 分语言能力包、配置和验证适配 | M2 的实用协议 | 每语言 M–L | 逐语言扩大语义闭环，而非仅扩大解析数量 |
| M5 规模化与交付收口 | 部署、资源预算、全链路真实验收、可选运行时证据 | 基础工作随 M0 开始；各阶段收口 | M–L | 可持续运行、可部署、可复核 |

依赖主线为 `M0 → M1 → M2 → M3`；M2 的后端最小试验可与 M1 并行，生产联动仍需通过 M1 的证据契约。M4 按语言逐个交付，不能等待“全语言完成”才上线首个闭环。

### M0：让证据有边界，先修闭环入口

工作项：

- M0.1 ✅ 用当前源码与回归更新能力矩阵：9 种文件依赖语言、C# 仅 AST/定义、组件仅 script；区分专业语义与启发式候选。同步 Trace 参考中的过期描述。
- M0.2 ✅ 为审计补结构化状态和跳过原因；普通编辑可继续短输出，但冷缓存、无适用规则、过期与已检查无发现不能混为一谈。
- M0.3 ✅ 普通编辑和票据确认走同一 post-commit 审计出口；文件操作分派到适用审计，未支持的操作明确报告，不硬套桥接规则。
- M0.4 ✅ 缓存选择必须绑定工程身份及声明/编译配置。旧快照可作为“修改前证据”，不能未经校验就声称消费者仍是当前版本。
- M0.5 ✅ `/forge-status` 展示静态/原生/语义/验证后端的可用性、版本和限制；报告可用性不应隐式启动构建、安装或付费服务。
- M0.6 ✅ 区分查询范围、实际扫描范围与展示截断；重要消费者结果提供分页或明确无法完整取回的原因。分页绑定查询版本，不能混合不同快照；无法完整取得的候选不得直接生成“全量修改”计划。
- M0.7 ✅ 统一传递位置时区分符号范围与含 context 的正文范围，明确行列基数、UTF-16/字节偏移与 CRLF/BOM 处理。原始字节哈希校验原始内容，不能与归一化文本偏移混用。

验收：冷/热缓存、过期消费者、不同 declarations 配置、票据确认、取消、解析失败均有可区别状态；不得出现“未运行→通过”。非审计目标编辑不被强制全仓扫描，已有权限及票据回归不退化。

### M1：先交付 Electron 最小闭环

工作项：

- ~~M1.1 修改前显式查询 `exposes:` / `ipc:` / `impact:`，保存本次操作的基线范围；不要求所有普通编辑自动构图。~~ 已实施：`fftrace capture=true` 逐文件读字节、按同一份内容提取事实并落盘内容基线（24 小时 TTL、每工作区 20 条/128 MiB、末尾原子重命名）；`ffedit`/`ff_file` 的 `snapshotId` 在写锁内校验同一工作区、文件被覆盖且字节未变，`drift`/`not_covered`/`observed_only` 各自拒绝而不是暗示通过。不完整捕获降级为 `observed` 且不保存。
- M1.2 用当前 AST 事实比较 expose 对象/成员、IPC 注册与消费者；按实际变更范围复查受影响消费者，区分新增破坏与基线已有问题。文本名字只作为预筛，不能作为通过或“调用必失败”的最终依据。
- M1.3 冷态正式检查可以显式构图；写后即时建议仍使用有界快路径。完整前后核查放在 `ffcheck`，不让一次保存隐式承担全仓延迟。
- M1.4 `ffcheck` 先支持静态复查及验证计划；若宿主支持可审计的命令调用，再加入显式执行。返回每项状态、范围与证据，不只返回一个总布尔值。
- M1.5 由宿主实际执行类型检查/测试，将结果追加关联到原 batch；历史与卡片展示“已写入、静态通过、测试未跑”等不同事实，失败不自动撤销写入。证据另行追加关联，不回写旧批次；卡片缓存增加检查记录修订号及适用性状态，不能仅沿用 size/mtime 锚判断验证有效。
- M1.6 guidance 根据当前作用域的真实工具名引导下一步，保留 additive/takeover/缺失工具的不同路由，不把规划中的能力提前写进提示词。
- M1.7 验证写入、补改和回滚对全文索引/覆盖层、AST、Trace、卡片各自的新鲜度影响；复用已有刷新机制，有事件加速也必须保留版本复核，不引入全局索引重建作为每次编辑的默认动作。

验收场景：桥接成员从 `togglePin` 改为 `pinToggle`，有两个文件、多个消费者，其中一个通过局部别名访问。只改提供者必须报遗漏；全部改完后针对同一新版本复查；残留在注释/无关对象中的旧名字不应证明旧成员仍存在。动态属性、spread 或无法绑定的别名必须保留未知。

退出条件：同一场景从查找、读取、Trace、修改、发现遗漏、补改、检查到 history/cards 可完整走通；另外演示一次检查失败后的回滚预览、确认与再次复查。补改后搜索/读取须看到新内容，回滚后重新看到恢复内容且原验证不再作为当前通过。此阶段允许多次单文件编辑，不冒充跨文件原子重构。

### M2：JS/TS 符号语义通道

工作项：

- M2.1 在代表性项目上比较 TypeScript Language Service 的按需引用查询与 `createProgram + TypeChecker` 索引路径，固定版本、配置、查询和输入集合，先测冷/热延迟、内存、更新与取消。
- M2.2 首选交互式 Language Service 适配，隔离在可终止的工作进程；只用受支持接口，不自行重写 binding/type checker。若最小试验否决该方案，再依据证据采用批索引，不能同时先建设两套完整引擎。
- M2.3 首批操作为“位置→符号/定义”“符号→引用”和项目诊断；区分声明、读写引用、类型引用、调用位置。调用层次按后端真实能力接入，不把每条 reference 都标为 call。
- M2.4 给 `fftrace` 增加结构化位置选择参数和 references 操作；`ff_read` 可消费同一位置引用。现有 `symbol:` 名称查询保持定义检索定位，不偷偷改变语义；名称歧义时列候选，不能默认选第一个。
- M2.5 处理 tsconfig 多项目归属、项目引用、包 exports/imports、声明文件和依赖缺失。解析用的外部声明不必全部展现在结果里，但其版本/缺失必须影响覆盖与新鲜度。
- M2.6 后端不存在、崩溃、超时或只返回部分结果时，静态快图照常可用；文本兜底明确标成文本，不继续以“语义引用”名义输出。

验收集：同名不同作用域、成员与局部变量同名、别名导入、default/namespace/re-export、重载/接口、多 tsconfig、JS 动态属性、UTF-16 列坐标、CRLF、取消及后端重启。每个案例有人工标注的引用集合及明确未知项。

与旧研究的关系：旧研究倾向全量 Checker→SCIP，适合离线索引；本路线优先解决交互编辑后的按需引用与诊断，因此重新设置选型门槛。SCIP 保留为后续离线导入，不把它当语言引擎，不在第一阶段同时建设两条生产通道。

退出条件：新增语义查询确实能排除文本同名诱饵，并在编辑后更新；M1 的验证记录能消费类型诊断。没有证据支持时不宣称引用集合完备。

### M3：跨文件变更与恢复

工作项：

- M3.1 消费后端 rename/location edits 或显式引用修改建议，输出只读预览：涉及文件、基线哈希、编辑范围、理由、候选/未解析项与必需检查。M3 前先验证 M2 后端是否提供这些操作。
- M3.2 将预览交给现有施工底座应用；全路径授权、基线复核、重叠编辑检查必须在写入前完成。模型选择候选不等于解除权限限制。
- M3.3 复用多文件事务恢复与快照，不实现第二套文件写入器；同一计划关联一个批次或明确的一组批次。这里的事务是计划/恢复一致性，不承诺操作系统对所有文件同时原子可见。
- M3.4 `ff_file` 的文件/符号迁移接入同一预览；更新引用需要后端明确支持，否则只提供候选、保留手动模式。候选边不能直接驱动“全部替换”。
- M3.5 应用后对最终文件集合做语义/桥接复查、诊断差分和授权测试；半途中断、其它 Agent 修改、目标路径被替换均须被检测。恢复冲突停止并报告，不能强行覆盖外部工作。
- M3.6 回滚产生新批次并令相关旧检查失效；引用、卡片与检索覆盖更新必须观察到回滚后的内容。

验收：跨三文件 rename，第三文件有同名无关符号；预览后修改一个文件；中途 I/O 失败；文件移动后旧路径失效；回滚前存在后续修改。分别验证正确改动范围、拒绝过期计划、可恢复性和不覆盖外部工作。

退出条件：可交付一个真实跨文件 rename/move 闭环，且拒绝与恢复场景同样通过；后验失败与写入失败分开呈现，不自动回滚已授权完成的其它工作。

### M4：逐语言、逐框架补齐专业差距

每个后端先交付 definitions/references/diagnostics，再考虑 implementations、rename、call hierarchy；不要求所有后端实现同一组可选能力。M4.0 随第二个真实后端提炼通用适配接口和协议测试；各项具体启动、配置、坐标映射和验收步骤见[语言实施手册](forge-plan-m4.md)。

| 编号 / 推荐批次 | 对象与专业后端 | 重点补齐 | 必须包含的验收边界 |
|---|---|---|---|
| M4.1 / A | Rust / rust-analyzer | Cargo 工程、cfg/features、宏后的符号、trait/类型引用 | workspace members/exclude、路径依赖重命名、条件编译、proc macro/build.rs 权限与缺失状态 |
| M4.2 / A | Python / Pyright | venv/导入环境、typeshed、类型与成员引用 | src layout、namespace package、stub/实现、动态属性与运行时导入未知 |
| M4.3 / B | C/C++ / clangd | 翻译单元、预处理、宏、模板与重载、完整编译上下文 | 多构建变体、头文件归属、生成头、response/sysroot；缺配置不猜唯一答案 |
| M4.4 / B | Go / gopls | 构建约束、平台、包与对象绑定、接口实现 | go.work/replace、vendor、build tags、GOOS/GOARCH、cgo 环境 |
| M4.5 / C | Java / JDT LS | Maven/Gradle/classpath、JAR、类型成员与重载 | 多模块、生成源码、缺失 JAR；工程导入可能执行代码的边界 |
| M4.6 / C | C# / Roslyn 对应的可用语言服务 | 先补文件/工程入口，再接 Solution/MSBuild/程序集符号 | 后端与宿主适配最小试验、条件编译、多 target framework；不能只加 `.cs` 扩展就宣称支持 |
| M4.7 / C | Lua / LuaLS | 类型注解、宿主定义、require 环境、词法引用 | 动态 table/metatable/searcher；不承诺后端没有的调用层次 |
| M4.8 / D | Vue 语言服务 | 模板与 script 的组件/成员关系、虚拟文件映射 | 双向 source map、生成范围、模板事件；不能只复用普通 TS 文件坐标 |
| M4.9 / D | Svelte 语言服务 | 模板绑定、组件 props、生成代码映射 | 框架版本、预处理器执行边界；不沿用 Vue 的语义实现 |

这些能力包可按实际工作区使用频率调整顺序；推荐不是技术上必须先 Rust 才能 Go。每语言独立宣布覆盖范围和缺失项，不能用所有后端查询并集掩盖配置不一致。

M4.10 的 FFI 扩展先增加明确的构建/链接产物关联、导出名与声明类型证据；调用链、ABI 兼容验证、跨进程运行时追踪另设试验，不把同名命中升级为已证实调用。

### M5：规模化、部署与真实验收

各项默认预算、实现接点、测试命令与退出条件见[运行与验收手册](forge-plan-m5.md)。

- M5.1 资源：语义进程按工作区/项目复用，设内存、空闲回收、取消及超时边界；重查询不阻塞廉价文件图。不同后端的线程数作为基准参数记录。
- M5.2 新鲜度：文件/配置/依赖和后端版本改变时失效；事件用于加速，不代替正确性校验。只读快图的进程内缓存无需为了规划而强制改成数据库。
- M5.3 部署：先声明平台与后端支持矩阵、明确安装/发现机制，再做发行包；不隐式联网下载。核验原生二进制与源码/版本对应，保留缺失时的可用降级。
- M5.4 许可：逐个审查引入的包、服务器与分发条款；ProjectForge 原生 crate 的许可不能按本仓 MIT 处理，不能直接搬代码作为捷径。
- M5.5 可选 SCIP：导入用户提供的索引时核对生成器、根、源码/配置身份；陈旧或身份不明的索引只供参考，不能授权自动编辑。SCIP 不自带运行时完备性与边置信度。
- M5.6 可选运行时证据：用户明确授权后关联测试覆盖、IPC 观测或日志；标注观测场景、版本、时间。一次没观察到调用不证明不存在，默认不开探针。
- M5.7 质量与性能：将第六节的真值、负例、磁盘核验与噪声标定落成固定评测脚本；先固定输入和判据，再比较实现。
- M5.8 真实宿主验收：核验实际注册、作用域、审批、执行终态和历史关联，保留可复查的调用/结果；内部测试通过不代替真实 DSH 流程。

## 五、执行与数据边界

| 层级 | 允许的行为 | 默认限制 |
|---|---|---|
| 静态核心 | 已授权范围内读取源码、配置、二进制元数据 | 不执行工程 registry、构建文件或解释器；只读缓存不写回工程 |
| 语义服务 | 显式启用的已安装受信后端，在声明范围内分析 | 启动前审查插件加载、Cargo build/proc macro、Gradle/MSBuild、compiler probing 等隐式执行；无法禁止时需额外授权或降级 |
| 验证执行 | 经宿主权限层批准的具体检查 | 项目 scripts/测试本身也是代码执行；不以“只运行测试”为理由绕过确认、沙箱或网络边界 |

拟定执行适配器应使用结构化程序/参数/cwd，避免拼接未转义的路径或名称；需要 shell 的命令使用宿主原有审批通道。发现 package scripts 不等于获准执行；没有沙箱时不宣称存在隔离。

检查证据保存在插件私有数据区，复用现有工作区隔离与保留策略；限制体积、脱敏环境和日志，不保存凭据。关联哈希用于版本对应，不宣称本地可写日志具备防篡改认证。外部模型润色维持现有显式配置边界，不因新增验证默认发送源码或日志。

## 六、统一验收口径

### 6.1 必须通过的负例

- 无后端、没有缓存、结果截断、动态未知、检查跳过，均不能汇总为通过。
- 预览后变更、执行中变更、检查后变更，旧证据不得继续适用。实时文件模式只能报告已观察到的一致性；若要强一致验收，需在明确的隔离快照上运行，不能靠时间戳宣称冻结全仓。
- 相同名称不同作用域/对象、注释与字符串诱饵，不能误改或掩盖缺失成员。
- 部分 tests 通过、测试发现为零、超时、异常退出，不能包装成完整测试通过。
- 有既存诊断时，区分原有与新增；若行号变化或后端结果不稳定导致归因不确定，报告未知，不强行相减。
- 权限拒绝、进程崩溃、取消、磁盘错误、恢复冲突，不得丢失用户工作。
- 检查失败后不能自动降级规则再宣布成功；用户缩小范围必须留痕。

### 6.2 质量与性能指标

| 指标 | 如何获得 | 如何解释 |
|---|---|---|
| 文件边与符号引用 precision/recall | 小型人工真值 + 固定真实项目标注子集，分别统计 | 健康度、确定性与后端对拍不能代替真值；专业后端也不是动态语义全知 oracle |
| 覆盖与未知比例 | 按语言、配置、查询种类记录分母和遗漏原因 | 不能靠丢弃难例提高表面精度 |
| 改动遗漏/误改 | 提供者/消费者/同名诱饵 fixture 与真实重构任务 | 误改无关符号、陈旧证据放行、越权写入是阻断性失败 |
| 闭环效率 | 同一任务的工具轮次、输出量、人工补查次数 | 少调用不是唯一目标，必须同时保留正确性与可解释性 |
| 延迟与内存 | 同文件集合、同配置/线程数、冷/热/编辑后更新分开测 | 先测同实现噪声地板，再交错 A/B；不比较不同扫描范围的倍率 |
| 恢复能力 | 注入中断/冲突后核对磁盘内容、快照与台账 | 不只看工具返回 success，必须核对实际文件 |

每个阶段在实现前冻结本阶段测试输入与验收阈值；已有确定性 fixture 必须全部通过。真实性能预算先测基线再定，不在无测量时编造统一毫秒门槛。

### 6.3 交付要求

每个里程碑同时交付：实现与回归、当前能力/限制说明、一条自包含的 DSH 验收提示词，以及实际宿主会话日志中的调用/结果证据。工厂函数测试证明内部行为，不单独证明宿主注册、工具选择与联动已成功。

真实语料在原生与回退模式分别检查；语义后端缺失与可用模式均覆盖。默认不把图推导的测试候选当成完备测试集合：仍执行约定的必需 smoke/类型检查；只有明确可靠的测试依赖映射才允许进一步裁剪，未知时扩大检查或标记未覆盖。

## 七、首个可验收切片与后续决策

首批只承诺 M0 + M1，不等所有语言补齐。验收切片是“Electron 桥接成员改名，漏改被识别，补改后检查，历史可追溯，失败可预览恢复”。它直接复用现有 Trace、编辑、台账和卡片，收益不依赖新语言服务器。

建议拆成四个可独立评审的实现批次：

1. 审计状态、配置/版本身份、普通与票据入口一致性及负例。
2. 基于前后 AST 的桥接契约复查与新增/既存问题区分。
3. 薄检查入口和可核验的宿主执行结果关联；宿主接口不可用时如实降级。
4. history/cards/guidance 联动及真实 DSH 全链路验收。

随后根据 M2 最小试验决定 TS 后端，交付首个符号级闭环；再建设跨文件重构与其它语言适配。暂不建设通用图数据库、自动修复代理、全仓常驻预计算、多后端共识系统或万能工作流调度器。

这条路线的完成标志不是“多了多少工具”，而是：**每次改动都能说明依据、应用范围、检查范围、未解决项与恢复入口，而且这些说明绑定真实版本和实际证据。**
